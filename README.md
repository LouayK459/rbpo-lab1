# Лабораторная работа 4 — безопасность сервиса доставки

Группа БАС2401, вариант 8. Ветка `lab4` продолжает проект из `lab3`.
Приложение хранит отправления, маршруты и назначения в PostgreSQL через Spring Data JPA.
Spring Security проверяет учётные данные, роли и принадлежность отправлений. Данные сохраняются после перезапуска приложения.

## Требования

- JDK 21;
- PostgreSQL 18;
- Maven Wrapper из репозитория (`mvnw.cmd` в Windows, `./mvnw` в Linux/macOS).

В `pom.xml` используются Spring Boot 4.1.1, Spring MVC, Spring Data JPA, Spring Security и драйвер PostgreSQL.

## Сущности и связи

| Сущность | Таблица в схеме `delivery` | Назначение и связи |
| --- | --- | --- |
| `User` | `users` | Профиль пользователя; у отправителя может быть несколько отправлений |
| `Account` | `accounts` | Имя входа, хеш пароля, роль и статус; уникальный `user_id` ссылается на профиль |
| `Shipment` | `shipments` | Отправление с адресом, весом и статусом; `sender_id` ссылается на пользователя |
| `Route` | `routes` | Маршрут на дату с ограничением общего веса |
| `Stop` | `stops` | Адрес и порядковый номер остановки; `route_id` ссылается на маршрут |
| `ShipmentAssignment` | `shipment_assignments` | Назначение отправления на остановку; ссылки `shipment_id` и `stop_id` |

Учётная запись связана с профилем через `@OneToOne`, остальные ссылки — через `@ManyToOne`.
В JSON передаются ID связанных объектов. Учётная запись удаляется вместе с профилем.
Внешние ключи записей доставки запрещают удалять родительские записи, пока на них ссылаются дочерние.
Пара `(route_id, sequence_number)` уникальна. Частичный уникальный индекс запрещает
два активных назначения одного отправления, но сохраняет историю отменённых назначений.
В базе также проверяются допустимые статусы, положительные веса и номера остановок,
непустые имена и адреса, согласованность статусов со временем вручения.

## Подготовка новой базы

Этот раздел нужен для новой установки. Уже настроенную базу повторно создавать не нужно.
Скрипты выполняются один раз от администратора `postgres` в указанном порядке.
Запуск `seed.sql` необязателен.

Пример для PowerShell, путь к PostgreSQL при необходимости изменить:

```powershell
$pgBin = "C:\Program Files\PostgreSQL\18\bin"
& "$pgBin\psql.exe" -X -h 127.0.0.1 -U postgres -d postgres -W -v ON_ERROR_STOP=1 -c "CREATE DATABASE rbpo_lab4 OWNER postgres;"
& "$pgBin\psql.exe" -X -h 127.0.0.1 -U postgres -d rbpo_lab4 -W -v ON_ERROR_STOP=1 -f db/setup.sql
& "$pgBin\psql.exe" -X -h 127.0.0.1 -U postgres -d rbpo_lab4 -W -v ON_ERROR_STOP=1 -f db/schema.sql
# Необязательно: добавить пример данных.
& "$pgBin\psql.exe" -X -h 127.0.0.1 -U postgres -d rbpo_lab4 -W -v ON_ERROR_STOP=1 -f db/seed.sql
```

`setup.sql` создаёт схему `delivery` и роль `rbpo_lab4_app` без прав администратора,
создания баз, ролей или объектов в этой схеме. Роль получает подключение к базе,
доступ к схеме, операции SELECT/INSERT/UPDATE/DELETE для таблиц и использование последовательностей.
Владельцем схемы и таблиц остаётся `postgres`. Права для новых таблиц и последовательностей
выдаются через `ALTER DEFAULT PRIVILEGES` для объектов, создаваемых ролью `postgres`.

Пароль приложения задать отдельно; он вводится скрыто и не хранится в SQL-файлах:

```powershell
& "$pgBin\psql.exe" -X -h 127.0.0.1 -U postgres -d rbpo_lab4 -W -v ON_ERROR_STOP=1 -c "SET password_encryption = 'scram-sha-256';" -c '\password rbpo_lab4_app'
```

`seed.sql` добавляет связанный пример: отправителя, маршрут, отправление, остановку
и назначение. Скрипт выводит созданные ID; полагаться на конкретные номера не нужно.

## Запуск

Открыть консоль в корне проекта. `JAVA_HOME` должен указывать на установленный JDK 21;
версию можно проверить командой `.\mvnw.cmd -v`.

```powershell
& {
    $env:DB_URL = "jdbc:postgresql://127.0.0.1:5432/rbpo_lab4"
    $env:DB_USERNAME = "rbpo_lab4_app"
    $env:DB_PASSWORD = [System.Net.NetworkCredential]::new("", (Read-Host "Password for rbpo_lab4_app" -AsSecureString)).Password
    $env:SERVER_ADDRESS = "127.0.0.1"
    $env:BOOTSTRAP_DISPATCHER_USERNAME = "dispatcher"
    $env:BOOTSTRAP_DISPATCHER_PASSWORD = [System.Net.NetworkCredential]::new("", (Read-Host "Dispatcher password" -AsSecureString)).Password
    .\mvnw.cmd spring-boot:run
}
```

При первом запуске создаётся диспетчер. Для него нужен отдельный пароль от 12 символов
до 72 байт UTF-8, с прописной и строчной буквой, цифрой и специальным символом.
Существующую учётную запись повторный запуск не меняет; после её создания переменные
`BOOTSTRAP_DISPATCHER_*` можно убрать.

Сервер доступен по адресу `http://127.0.0.1:8080`. Переменные действуют в этой консоли
и запущенных из неё процессах. В настройках запуска IDE их нужно задать отдельно.
`application.yml` читает реквизиты подключения из окружения. Hibernate проверяет готовую
структуру (`ddl-auto: validate`), а не создаёт таблицы при запуске.

## Аутентификация и доступ

| Запрос | Доступ и результат |
| --- | --- |
| GET `/api/auth/csrf` | Доступен без входа; возвращает имя заголовка и CSRF-токен |
| POST `/api/auth/register` | Доступен без входа с CSRF-токеном; тело: `name`, `username`, `password`; создаёт активного отправителя |
| GET `/api/auth/me` | Данные вошедшего пользователя: ID записи, ID профиля, имя входа, роль и статус |
| GET `/api/accounts` | Диспетчер просматривает учётные записи |
| PATCH `/api/accounts/{id}/status` | Диспетчер устанавливает `ACTIVE` или `BLOCKED` полем `status`; блокировать свой аккаунт нельзя |

Имена входа приводятся к нижнему регистру и уникальны. При публичной регистрации роль всегда
`SENDER`. В PostgreSQL сохраняется хеш BCrypt; API не возвращает пароль или его хеш.
Защищённые запросы используют HTTP Basic. Для POST, PATCH и DELETE нужно получить
токен с `/api/auth/csrf`, отправить его в `X-CSRF-TOKEN` и сохранить cookie той же сессии.
Cookie сессии сама по себе не даёт доступа к защищённым запросам.

`DISPATCHER` управляет профилями, отправлениями, маршрутами, остановками и назначениями.
`SENDER` может читать, менять и удалять свой профиль по ID и работать со своими отправлениями
с учётом бизнес-ограничений. Создать отправление на чужой ID или передать своё чужому
отправителю нельзя. Список отправлений фильтруется по владельцу в базе.
Доступ проверяется в цепочке фильтров Spring Security и на методах с `@PreAuthorize`.

Отсутствующие или неверные учётные данные и вход заблокированного аккаунта дают 401.
Недостаточные права или отсутствующий либо неверный CSRF-токен дают 403.
Невалидные реквизиты регистрации дают 400, повторное имя входа — 409.

## REST API

Диспетчеру для каждого ресурса доступны GET списка, GET `/{id}`, POST, PATCH `/{id}` и DELETE `/{id}`:

- `/api/users`;
- `/api/shipments`;
- `/api/routes`;
- `/api/stops`;
- `/api/shipment-assignments`.

Создание возвращает 201, чтение и изменение — 200, удаление — 204.
Некорректные данные дают 400, отсутствующая запись — 404, нарушение правил — 409.
Тело ошибки содержит `error` и `timestamp`.

Новые маршруты имеют статус `PLANNED`, отправления — `CREATED`, назначения — `ASSIGNED`.
Адрес отправления должен совпадать с адресом остановки. Назначать отправления и менять
маршрут можно до выезда. Сумма весов активных назначений не должна превышать `maxWeight`.
Нельзя увеличить вес уже назначенного отправления или уменьшить лимит маршрута ниже его загрузки.
Статусы меняются бизнес-операциями; PATCH не позволяет пропустить этапы доставки.
`createdAt`, `deliveredAt` и `completedAt` задаёт сервер.

## Пять бизнес-операций

| Запрос POST | Условия и результат |
| --- | --- |
| `/api/routes/{id}/start` | Маршрут `PLANNED` с назначенными отправлениями допустимого общего веса. Маршрут и назначения становятся `IN_PROGRESS`, отправления — `IN_TRANSIT` |
| `/api/shipment-assignments/{id}/complete` | Маршрут и назначение в работе. Назначение становится `COMPLETED`, отправление — `DELIVERED`; в обеих записях сохраняется время вручения |
| `/api/routes/{id}/complete` | Маршрут в работе, все неотменённые доставки завершены. Маршрут становится `COMPLETED` |
| `/api/routes/{id}/cancel` | Только до выезда. Маршрут и его назначения становятся `CANCELLED`; отправления остаются `CREATED` и доступны для нового назначения |
| `/api/routes/{id}/repeat` | Только завершённый маршрут. Тело `{"date":"2030-01-01"}` с будущей датой позже исходной. Создаются новый маршрут `PLANNED` и копии остановок; отправления и назначения не копируются |

Изменения одной операции выполняются в одной транзакции. Сервисы используют
`@Transactional(isolation = Isolation.SERIALIZABLE)`. Найденные сущности управляются JPA,
поэтому изменения их полей сохраняются при завершении транзакции.
При ошибке изменения откатываются. При конфликте параллельных транзакций возвращается 409;
клиент может повторить запрос. Автоматического повтора нет.
Завершённые и отменённые доставки сохраняются как история.

## Проверка

В консоли с настроенными переменными подключения:

```powershell
.\mvnw.cmd clean verify
```

`Lab3DatabaseTests` использует тестовую роль диспетчера и проверяет CRUD с чтением заново из PostgreSQL, изменения связанных
статусов и времени вручения, копирование маршрута, отмену и переназначение, ограничения
веса и статусов. Отдельный тест принудительно вызывает ошибку после записи в пять таблиц
и проверяет откат в новой транзакции. Тестовые записи откатываются; пропуски в ID возможны,
так как значения последовательностей PostgreSQL не откатываются.

Импортировать [коллекцию лабораторной 4](requests/lab4.postman_collection.json) в Postman.
В локальных значениях переменных задать `dispatcherPassword` и при необходимости
`dispatcherUsername` (по умолчанию `dispatcher`). Пароль диспетчера в файле коллекции пуст.
Запустить все 95 запросов по порядку с включёнными cookies и работающим приложением.
Ожидаемый результат: 150 пройденных проверок, 0 ошибок.

Коллекция сама получает CSRF-токен, генерирует реквизиты тестового отправителя, даты и ID.
Первый раздел проверяет вход, отказы регистрации, попытку повысить роль, доступ к чужим
данным, блокировку и разблокировку. Второй проверяет CRUD пяти сущностей, третий — пять
бизнес-операций и их ограничения. Тестовые записи первых двух разделов удаляются,
а завершённые и отменённые доставки последнего остаются в истории.

Для проверки сохранности данных можно прочитать списки маршрутов и отправлений,
остановить и запустить приложение, затем повторить GET: записи и статусы должны сохраниться.
