# Лабораторная работа 3 — сервис доставки

Группа БАС2401, вариант 8. Ветка `lab3` продолжает проект из `lab2`.
Приложение хранит отправления, маршруты и назначения в PostgreSQL через Spring Data JPA.
Данные сохраняются после перезапуска приложения.

## Требования

- JDK 21;
- PostgreSQL 18;
- Maven Wrapper из репозитория (`mvnw.cmd` в Windows, `./mvnw` в Linux/macOS).

В `pom.xml` используются Spring Boot 4.1.1, Spring MVC, Spring Data JPA и драйвер PostgreSQL.

## Сущности и связи

| Сущность | Таблица в схеме `delivery` | Назначение и связи |
| --- | --- | --- |
| `User` | `users` | Отправитель; у пользователя может быть несколько отправлений |
| `Shipment` | `shipments` | Отправление с адресом, весом и статусом; `sender_id` ссылается на пользователя |
| `Route` | `routes` | Маршрут на дату с ограничением общего веса |
| `Stop` | `stops` | Адрес и порядковый номер остановки; `route_id` ссылается на маршрут |
| `ShipmentAssignment` | `shipment_assignments` | Назначение отправления на остановку; ссылки `shipment_id` и `stop_id` |

Связи в JPA задаются через `@ManyToOne`. В JSON передаются ID связанных объектов.
Внешние ключи запрещают удалять родительские записи, пока на них ссылаются дочерние.
Пара `(route_id, sequence_number)` уникальна. Частичный уникальный индекс запрещает
два активных назначения одного отправления, но сохраняет историю отменённых назначений.
В базе также проверяются допустимые статусы, положительные веса и номера остановок,
непустые имена и адреса, согласованность статусов со временем вручения.

## Подготовка новой базы

Этот раздел нужен для новой установки. Уже настроенную базу повторно создавать не нужно.
Скрипты выполняются один раз от администратора `postgres` в указанном порядке.

Пример для PowerShell, путь к PostgreSQL при необходимости изменить:

```powershell
$pgBin = "C:\Program Files\PostgreSQL\18\bin"
& "$pgBin\psql.exe" -X -h 127.0.0.1 -U postgres -d postgres -W -v ON_ERROR_STOP=1 -c "CREATE DATABASE rbpo_lab3 OWNER postgres;"
& "$pgBin\psql.exe" -X -h 127.0.0.1 -U postgres -d rbpo_lab3 -W -v ON_ERROR_STOP=1 -f db/setup.sql
& "$pgBin\psql.exe" -X -h 127.0.0.1 -U postgres -d rbpo_lab3 -W -v ON_ERROR_STOP=1 -f db/schema.sql
& "$pgBin\psql.exe" -X -h 127.0.0.1 -U postgres -d rbpo_lab3 -W -v ON_ERROR_STOP=1 -f db/seed.sql
```

`setup.sql` создаёт схему `delivery` и роль `rbpo_lab3_app` без прав администратора,
создания баз, ролей или объектов в этой схеме. Роль получает подключение к базе,
доступ к схеме, операции SELECT/INSERT/UPDATE/DELETE для таблиц и использование последовательностей.
Владельцем схемы и таблиц остаётся `postgres`. Права для новых таблиц и последовательностей
выдаются через `ALTER DEFAULT PRIVILEGES` для объектов, создаваемых ролью `postgres`.

Пароль приложения задать отдельно; он вводится скрыто и не хранится в SQL-файлах:

```powershell
& "$pgBin\psql.exe" -X -h 127.0.0.1 -U postgres -d rbpo_lab3 -W -c "SET password_encryption = 'scram-sha-256';" -c '\password rbpo_lab3_app'
```

`seed.sql` добавляет связанный пример: отправителя, маршрут, отправление, остановку
и назначение. Скрипт выводит созданные ID; полагаться на конкретные номера не нужно.

## Запуск

Открыть консоль в корне проекта. `JAVA_HOME` должен указывать на установленный JDK 21;
версию можно проверить командой `.\mvnw.cmd -v`.

```powershell
$env:DB_URL = "jdbc:postgresql://localhost:5432/rbpo_lab3"
$env:DB_USERNAME = "rbpo_lab3_app"
$env:DB_PASSWORD = [System.Net.NetworkCredential]::new("", (Read-Host "Password for rbpo_lab3_app" -AsSecureString)).Password
.\mvnw.cmd spring-boot:run
```

Сервер доступен по адресу `http://localhost:8080`. Переменные действуют в этой консоли
и запущенных из неё процессах. В настройках запуска IDE их нужно задать отдельно.
`application.yml` читает реквизиты подключения из окружения. Hibernate проверяет готовую
структуру (`ddl-auto: validate`), а не создаёт таблицы при запуске.

## REST API

Для каждого ресурса доступны GET списка, GET `/{id}`, POST, PATCH `/{id}` и DELETE `/{id}`:

- `/api/users`;
- `/api/shipments`;
- `/api/routes`;
- `/api/stops`;
- `/api/shipment-assignments`.

Создание возвращает 201, чтение и изменение — 200, удаление — 204.
Некорректные данные дают 400, отсутствующая запись — 404, нарушение правил — 409.
Тело ошибки содержит `error` и `timestamp`.

Новые маршруты имеют статус `PLANNED`, отправления — `CREATED`, назначения — `ASSIGNED`.
Адрес отправления должен совпадать с адресом остановки. Назначать отправления и менять
маршрут можно до выезда. Сумма весов активных назначений не должна превышать `maxWeight`.
Нельзя увеличить вес уже назначенного отправления или уменьшить лимит маршрута ниже его загрузки.
Статусы меняются бизнес-операциями; PATCH не позволяет пропустить этапы доставки.
`createdAt`, `deliveredAt` и `completedAt` задаёт сервер.

## Пять бизнес-операций

| Запрос POST | Условия и результат |
| --- | --- |
| `/api/routes/{id}/start` | Маршрут `PLANNED` с назначенными отправлениями допустимого общего веса. Маршрут и назначения становятся `IN_PROGRESS`, отправления — `IN_TRANSIT` |
| `/api/shipment-assignments/{id}/complete` | Маршрут и назначение в работе. Назначение становится `COMPLETED`, отправление — `DELIVERED`; в обеих записях сохраняется время вручения |
| `/api/routes/{id}/complete` | Маршрут в работе, все неотменённые доставки завершены. Маршрут становится `COMPLETED` |
| `/api/routes/{id}/cancel` | Только до выезда. Маршрут и его назначения становятся `CANCELLED`; отправления остаются `CREATED` и доступны для нового назначения |
| `/api/routes/{id}/repeat` | Только завершённый маршрут. Тело `{"date":"2030-01-01"}` с будущей датой позже исходной. Создаются новый маршрут `PLANNED` и копии остановок; отправления и назначения не копируются |

Изменения одной операции выполняются в одной транзакции. Сервисы используют
`@Transactional(isolation = Isolation.SERIALIZABLE)`. Найденные сущности управляются JPA,
поэтому изменения их полей сохраняются при завершении транзакции.
При ошибке изменения откатываются. При конфликте параллельных транзакций возвращается 409;
клиент может повторить запрос. Автоматического повтора нет.
Завершённые и отменённые доставки сохраняются как история.

## Проверка

В консоли с настроенными переменными подключения:

```powershell
.\mvnw.cmd clean verify
```

`Lab3DatabaseTests` проверяет CRUD с чтением заново из PostgreSQL, изменения связанных
статусов и времени вручения, копирование маршрута, отмену и переназначение, ограничения
веса и статусов. Отдельный тест принудительно вызывает ошибку после записи в пять таблиц
и проверяет откат в новой транзакции. Тестовые записи откатываются; пропуски в ID возможны,
так как значения последовательностей PostgreSQL не откатываются.

В `requests/lab3.postman_collection.json` находится коллекция из 71 запроса.
Импортировать её в Postman и выполнить целиком по порядку при работающем сервере.
`baseUrl` по умолчанию равен `http://localhost:8080`.
Коллекция сама создаёт данные, получает ID из ответов и формирует даты; начальные ID из
`seed.sql` ей не нужны. Первый раздел проверяет CRUD всех сущностей и удаляет свои записи.
Второй проходит пять бизнес-операций и проверки отказов; его завершённые и отменённые
доставки остаются в истории. Скрипты Postman проверяют коды и важные поля ответов.

Для проверки сохранности данных можно прочитать списки маршрутов и отправлений,
остановить и запустить приложение, затем повторить GET: записи и статусы должны сохраниться.
